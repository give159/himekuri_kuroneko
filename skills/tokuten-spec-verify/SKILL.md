# 【特典】仕様書を書いて、機械的に検証する

仕様書の事故は、文章が下手だから起きるのではありません。
**要件が設計に落ちていない／受入基準が空のまま承認された／IDが重複して指摘が迷子になる**——
こうした「対応関係の穴」が原因です。読んでも見つからないので、数えて確かめます。

## いつ使うか
- 要件定義書・詳細設計書・仕様書を作る・レビューする・整合を確認するとき
- 「この要件、ちゃんと設計に反映できてる？」を確かめたいとき

## 書き方のルール（検証できる形にする）

### 1. すべてにIDを振る
- 要件：`REQ-001`, `REQ-002` …
- 設計：`DSG-001` … 各設計は「どの要件を満たすか」を明記（例：`→ REQ-003`）
- テスト：`TST-001` … 各テストは「どの要件を確かめるか」を明記

### 2. 受入基準を空にしない
各要件に「どうなったら満たしたと言えるか」を必ず1行書く。

### 3. 対応関係（トレーサビリティ）を残す
「要件 → 設計 → テスト」が1本の線でつながるようにする。

## 検証の観点（目視でなくチェックで）
- [ ] すべての要件IDが一意（重複なし）
- [ ] すべての要件に受入基準がある（空がない）
- [ ] すべての要件に、それを満たす設計が最低1つある（孤立要件なし）
- [ ] すべての設計が、いずれかの要件に紐づく（宙に浮いた設計なし）
- [ ] すべての要件に、確認するテストがある

この5点が全部OKになるまで「完成」と言わないこと。

## 進め方
1. 要件を箇条書き＋IDで書く（`references/templates.md` のひな形）
2. 各要件に受入基準を足す
3. 設計を書き、各設計に `→ REQ-xxx` を付ける
4. テストを書き、各テストに `→ REQ-xxx` を付ける
5. 上の5観点を1つずつ確認（抜けがあれば埋める）

## 参照ファイル
- `references/templates.md` … 要件定義書・詳細設計書・テスト表のひな形
- 機械検証を自動化したい場合は、ID抽出→対応チェックの小スクリプトを書くとよい
  （「REQ-xxxに対応する設計があるか」を数えるだけ。目視より速く確実）

## 出典（嘘をつかない）
標準を参照するときは確認済みのもののみ（例：ISO/IEC/IEEE 15288、INCOSE Handbook、
ISO/IEC 25010:2023）。存在しない規格番号や条項をでっち上げない。

*面白きこともなき世を面白く。*
